# AGENT.md

## Description
This repo is the declarative source of truth for a single-user homelab platform, GitOps-managed by Flux, exposed over Tailscale, and observed via kube-prometheus-stack. On top of it, a self-service typed platform API (kro) provisions `Database`/`ObjectStorage`/`Application` instances for other repos. Full product concept lives in `CONCEPT.md`.

**The node platform is mid-migration (D20) from a single Talos VM to a bare-metal multi-node fleet, and both currently coexist.** `clusters/homelab/` is the original shape: an Ubuntu host bootstrapped with Ansible into a hypervisor, running one Talos VM under Terraform (`terraform/modules/talos-cluster/`). `clusters/homelab-metal/` is the new shape: Talos installed directly on bare metal, no hypervisor, provisioned by `terraform/modules/talos-metal/` — currently just machine 2 (`homelab-worker-0`), with machine 1 (the original laptop) slated to join later as a worker per `fleet/nodes.yaml`. Both Flux entrypoints reconcile the **same** `infrastructure/` tree during the migration — deliberately, so the VM stays a working rollback — which means an `infrastructure/` change (e.g. the Longhorn/Cilium changes below) lands on both clusters at once. `clusters/homelab/` retires once the metal fleet is proven; see `docs/adr/0001-single-model-talos-fleet.md` for the rationale, which is still marked DRAFT despite the build being under way.

## Repo layout
- `ansible/` — **the metal only, for the original VM-hosting machine** (idempotent). `playbooks/converge.yml` runs roles in order: `host_prereqs` → `bulk_storage` → `cli_tools` → `heartbeat_watchdog`, covering packages, firewall, libvirt networks/pools and the operator's CLI tools. It stops where a VM can be created; the VM, the cluster and its workloads belong to `terraform/` and Flux. Bare-metal fleet machines (`clusters/homelab-metal/`) run Talos directly and are never touched by Ansible — see `fleet/` below. Inventory/vars in `ansible/inventory/hosts.ini`.
- `infrastructure/` — Flux-managed Kubernetes manifests (HelmRepositories, HelmReleases, namespaces, SOPS-encrypted secrets), one subdirectory per component:
  - `flux-notifications/` — a notification `Provider`+`Alert` so Flux reports its own reconciliation failures to ntfy. `error` severity only: Flux emits a success event per object per interval, and routing those would bury the one message that matters. Exists because a failed Kustomization is otherwise completely silent — `personal-finance-dashboard` sat broken from the Talos cutover until someone happened to run `kubectl get kustomization -A`.
  - `tailscale-operator/`, `observability/`, `sources/` — platform scaffolding.
  - `storage/` + `longhorn/` — three StorageClasses named for their guarantee, not their implementation: `scratch` (disposable, Delete, still a single local-path-provisioner instance in `storage/`), `fast` and `bulk` (both durable, Retain, backed by Longhorn since D20, selected by **disk tag** rather than path — see `fleet/nodes.yaml`). **No class is default**, so a PVC naming none stays Pending rather than landing somewhere wrong; Longhorn's own chart default class is deliberately turned off for the same reason. See `docs/storage-tiering-notes.md` for the tiering rationale (its class names/mechanics predate this Longhorn move — see that file's header note).
  - `kro/` — the kro operator (`rbac.mode: aggregation`; its privilege doc is `platform-api/rbac-kro-aggregate.yaml`, extend it when a new kind is added to an RGD).
  - `platform-api/` — the `Database`/`ObjectStorage`/`Application` `ResourceGraphDefinition`s (`platform.homelab/v1alpha1`), per decision D15. Like `seaweedfs-runtime/`, its **own** Flux Kustomization (`dependsOn: [infrastructure]`) — the RGDs' CRD comes from the kro HelmRelease alongside them, which deadlocks a cold apply if they share a Kustomization.
  - `tailscale-runtime/` — the `ProxyGroup` exposing the apiserver to the tailnet (`kube-apiserver-ci`, noauth mode). Its **own** Flux Kustomization for the same cold-apply reason as `seaweedfs-runtime/` — the `ProxyGroup` CRD comes from the tailscale-operator HelmRelease.
  - `app-registrar/` — the RBAC + `ValidatingAdmissionPolicy` letting an app repo's CI register its own Flux pointer objects. Plain `infrastructure/` (no CRDs involved). See `docs/zero-touch-app-registration.md`.
  - `human-auth/` — the `ClusterRole` for the operator's own Google-OIDC identity once the apiserver accepts a Google-issued token (`AuthenticationConfiguration` in the relevant `talos.tf`). Plain built-in kinds, same reasoning as `app-registrar/`.
  - `postgres/` — CloudNativePG operator, backing every `Database` instance.
  - `seaweedfs/` — SeaweedFS operator + HelmRelease.
  - `seaweedfs-runtime/` — the `Seaweed` cluster/`ResourceReferenceGrant`/`PodMonitor`s, deliberately its **own** Flux Kustomization (`dependsOn: [infrastructure]`) — pairing a HelmRelease with CRD-dependent raw manifests in the same Kustomization deadlocks on cold apply, found building this component; see `docs/journal/` for the build gotchas.
  - `victoria-metrics/` — VictoriaMetrics single-node, the long-term store for power/energy history. Runs in the `observability` namespace and receives a **filtered** `remoteWrite` from Prometheus (`node_rapl_*` only). Exists because Prometheus retention is global — there is no per-series routing, so keeping five series for years without keeping all ~64k would be impossible in one TSDB. Its PVC is on the `bulk` tier; see `docs/storage-tiering-notes.md`.
  - `cilium/` — on the metal cluster (`clusters/homelab-metal/`), **the only CNI and the only thing programming Services**: Talos renders neither Flannel nor kube-proxy there (`cluster.network.cni.name: none`, `cluster.proxy.disabled: true` in `terraform/modules/talos-metal/`), and Cilium replaces both (`kubeProxyReplacement: true`). This is a change from the original design, where Cilium chained onto Flannel in `generic-veth` mode purely to give `NetworkPolicy` a policy backend — Talos's default CNI (Flannel) has none, so every policy was inert until Cilium landed. That chaining-mode reasoning still applies wherever the VM cluster (`clusters/homelab/`) is still running Flannel, since Talos bootstrap manifests don't retrofit (see below) and both clusters reconcile this same HelmRelease. Lives in `kube-system` (the one namespace Talos exempts from PodSecurity). See `docs/networkpolicy-enforcement-notes.md`.
  - `metrics-server/` — metrics-server plus a vendored `kubelet-serving-cert-approver`. Talos bundles neither, and the kubelet self-signs its serving certificate, so `kubectl top` needs both these *and* `rotate-server-certificates` in `terraform/` — any one of the three alone does nothing.
  - **No per-app directories, deliberately.** An app's Flux pointer objects (`GitRepository`+`Kustomization`) are created by the app repo's own CI, not committed here — see `app-registrar/` and `docs/zero-touch-app-registration.md`. `fastapi-echo/` and `personal-finance-dashboard/` used to live here and were removed once their repos self-registered. Adding a directory named after an application is the signature of that feature having regressed.
- `fleet/` — **the node inventory** (`nodes.yaml`): every hardware fact about every machine, and the only place they appear. Per node: role, zone, MAC, address, install **disk selector** and Longhorn disks with their tags. Consumed by `terraform/clusters/homelab-metal/` via `yamldecode`. Stage 2 of `docs/fleet/inventory-and-provisioning-approach.md`, and deliberately **data rather than HCL** so it can feed something else later — it maps onto Tinkerbell's `Hardware` field-for-field, so this fleet can be adopted into netboot without reinstalling. Not a CRD: nothing reconciles a machine that has not joined yet, so this is push-reconciled by `terraform apply`, the same shape as `tailscale-acl/`. **Adding a machine is a block here plus one apply** — and you do not need to know the machine's address: Talos in maintenance mode DHCPs on every physical interface, and `terraform/scripts/discover-maintenance-node.sh` resolves it from the MAC (ARP, not a port scan — ARP maps MAC to address directly, which is the lookup the inventory gives you). A DHCP reservation would also work and was rejected for not being version-controlled. Discovery runs only for nodes named in `dial_over_lan`, so an ordinary plan never shells out. — certSANs, tailnet name, ACL membership, disk tags and zone label all derive from it.
- `scripts/` — operator tools that are not part of any deployed artifact. Currently one: `platform-render`, which shows the raw Kubernetes objects behind a `platform.homelab` type — `preview` for an unapplied instance (schema validation plus every default filled in), `eject` for a live one (every object kro rendered, cleaned into appliable manifests). This is CONCEPT.md's "layer 2 renders its layer 1 output visibly" requirement made real; see `docs/platform-api-usage.md`.
- `terraform/` — machine and cluster lifecycle, two modules for the two node platforms currently coexisting. `modules/talos-cluster/` builds a libvirt domain + three volumes and bootstraps Talos on it (instantiated by `clusters/homelab/`, née `terraform/clusters/homelab/`); `modules/talos-metal/` bootstraps Talos directly on bare metal from `fleet/nodes.yaml`, no libvirt provider (instantiated by `terraform/clusters/homelab-metal/`). Operating manual for both, including the out-of-band-PKI secrets workflow and the pool-path safety rule, is in `terraform/README.md`.
- `tailscale-acl/` — the tailnet's access-control policy (`policy.hujson`): tags, ACL rules, Grants, autoApprovers. A sibling of `ansible/`/`terraform/`/`infrastructure/`, not a subdirectory, because Tailscale's control plane is a fourth one — not something Flux can reconcile. Applied by `.github/workflows/tailscale-acl.yml` (the repo's only GitHub Actions workflow), which is therefore the one path here that writes to live infrastructure without going through Flux. Operating manual, including the workload-identity-federation setup, is in `tailscale-acl/README.md`. Not to be confused with `infrastructure/tailscale-operator/`, which is the operator running *inside* the cluster.
- `clusters/` — Flux's entrypoint Kustomizations, one subdirectory per cluster, each pointing at the **same** `infrastructure/` tree (and, separately, `infrastructure/seaweedfs-runtime/` and `infrastructure/platform-api/`). `clusters/homelab/` is the original VM cluster's entrypoint; `clusters/homelab-metal/` is the bare-metal fleet's, added for the D20 migration. Both are live simultaneously by design during the migration — see the Description above.
- `CONCEPT.md` — the short product concept: what this platform is and why. Not a decision log — prior revisions with a full numbered decision history are in git history; current-state detail lives in this file and `docs/`.
- `docs/` — supplementary notes, one subdirectory for dated journal entries (`journal/`) and one for architecture decision records (`adr/`, being reorganized separately). **See `docs/README.md` for the index** — every doc, one line each, organized by area; don't enumerate them here, keep that one file as the map so descriptions live in exactly one place.

## Key operational facts
- **Ansible escalates only via a NOPASSWD sudoers drop-in — no released ansible-core can do password-based become here.** Ubuntu 26.04's `sudo-rs` wraps Ansible's prompt marker inside its own `[sudo: <marker>] Password:` rather than replacing it, and Ansible matches with `startswith()`, so `-K` hangs until it times out. Fixed upstream but unreleased; the full analysis and its expiry condition are in the comment block in `ansible.cfg`. Hosts are reached over SSH, so run playbooks plainly:
  ```
  ansible-playbook -i ansible/inventory/hosts.ini ansible/playbooks/converge.yml --tags <tags>
  ```
  Scope with `--tags` (`host_prereqs`, `bulk_storage`, `cli_tools`, `heartbeat_watchdog`) to avoid tripping unrelated guards — e.g. `heartbeat_watchdog` hard-fails until a real `ntfy_topic` replaces the `CHANGEME` placeholder in `hosts.ini`.
  **Neither `-K` nor a top-level `sudo`.** The `sudo` wrapper was correct only while the inventory said `ansible_connection=local`; now it would run Ansible as root on the *control node*, looking for root's SSH key and root's age key and finding neither. A new machine gets its drop-in at OS-install time (`docs/fleet/headless-ubuntu.md`'s `late-commands`); machine 1's was planted by hand. `become_flags = -H -n` is what makes a *missing* drop-in fail fast instead of hanging on a prompt nobody will answer.
- **The ntfy topic exists in THREE encrypted files, and rotation means editing all three.** `ansible/inventory/group_vars/homelab/ntfy_topic.sops.yaml` (host watchdog), `infrastructure/observability/alertmanager-ntfy-secret.sops.yaml` (Alertmanager's critical route) and `infrastructure/flux-notifications/ntfy-secret.sops.yaml` (Flux's Provider — which cannot reference a Secret outside its own namespace). Duplication was chosen over a shared source deliberately: the three consumers sit on opposite sides of the Ansible/Flux boundary and across namespaces, for a value that changes approximately never. Miss one and that consumer shouts into a topic nobody reads.
- **Secrets are SOPS-encrypted with age**, scoped to `infrastructure/**/*.sops.yaml`, only the `data`/`stringData` fields (see `.sops.yaml`) so diffs on rotation stay legible.
- **Version pinning convention**: chart versions (`HelmRelease.spec.chart.spec.version`), CLI tool versions (`ansible/roles/cli_tools/vars/main.yml`), and collection versions (`ansible/requirements.yml`) are pinned explicitly with a comment noting when/against-what they were last re-verified. Re-check before bumping, don't leave things unpinned to "always get latest."
- **Flux v2.8.8's controllers no longer export object status.** `gotk_suspend_status` and `gotk_reconcile_condition` are gone — the controllers serve only reconcile durations and token-cache counters. Flux object state (`ready`, `suspended`, `revision`) now comes from kube-state-metrics reading the CRs, configured as `customResourceState` in `infrastructure/observability/helmrelease.yaml`, and surfaces as `gotk_resource_info`. Two traps in that series: the `suspended` label is **absent**, not `"false"`, when a resource is not suspended (so match `suspended="true"`, never `suspended!="true"`), and `ready` stays `True` while suspended — a suspended resource looks healthy everywhere else.
- **Flux tracks `main`, so a change on an unmerged branch is not live** no matter how correct it looks. Check `kubectl get kustomization -A` and `kubectl get helmreleases -A` before assuming a manifest took effect. (Terraform still stops at an empty cluster by design — `flux bootstrap` is a separate step, and would be again after a rebuild.)
- **Talos bootstrap manifests don't update in place** — a machine-config change to kube-proxy, CoreDNS or flannel reaches the cluster on a *rebuild*, not on `terraform apply`. Talos re-renders them at once (the `Manifest` resource bumps version, `ManifestApplyController` logs no error) but will not push the new render onto an object that already exists — they carry `config.k8s.io/owning-inventory: talos-bootstrap-manifests-inventory` and are owned by `talos / Apply`. **The failure is silent**: Terraform reports success, `talosctl get machineconfig` shows the change, `talosctl get manifest <id> -o yaml` shows the new render, and the live object sits unchanged at its original generation. To land one on a live cluster, patch the object to match the render — that is catching up, not drift. Verified against v1.13.8, 2026-08-16.
- **NetworkPolicy enforces only because of `infrastructure/cilium/`, and only for pods created after it.** Talos's default CNI is Flannel, which accepts policy objects and enforces nothing — silently, with no admission error and no condition on the object, which is how three inert policies sat in `flux-system` unnoticed. Cilium chains onto Flannel to supply the missing backend. Two consequences that bite: a policy manifest predating this is **not** evidence anything was ever enforced, and a pod that predates the Cilium DaemonSet is **unmanaged by it** — still reachable, still working, simply not subject to policy, with nothing on the pod saying so. Suspect pod age first when one workload ignores a policy. Never trust a deny rule you have not watched fail; the test is in `docs/networkpolicy-enforcement-notes.md`.
- **Every `Application` is ingress-locked to its own Tailscale proxy, and that is what makes the identity headers believable.** Revision 5 of the Application RGD renders a `NetworkPolicy` per instance — no opt-in, no field to set. It permits TCP `spec.port` from that app's *own* proxy pod (`tailscale.com/parent-resource=<name>` + `parent-resource-ns=<namespace>`, so another app's proxy is not permitted) and from `observability`; egress is untouched. Two things follow. An app that needs ingress from anything else — another app calling it as an internal API — breaks as a connection timeout with nothing naming the policy, and the fix is an additive field on the API, not a hand-written policy in the app's repo. And if the app exposures ever move to a shared `ProxyGroup`, the proxy pods relabel to `parent-resource-type=proxygroup` and this rule matches **nothing**, breaking every `Application` at once; that migration edits the RGD in the same change. App-side contract: `docs/identity-headers.md`.
- **A default-deny ingress policy also denies the kubelet's probes, unless `infrastructure/cilium/allow-node-to-pods.yaml` is in place.** Under CNI chaining Cilium does not own Flannel's bridge, so probes arriving from `cni0` at `10.244.0.1` are classified `world`, not `host` — the "Cilium allows the host identity by default" intuition is false here. The symptom is a crash loop on probe timeouts while the process inside logs normal operation, and `kubectl describe pod` names only the probe, never the policy. `kubectl exec -n kube-system ds/cilium -- hubble observe --type drop` is where the real cause is. Deleting that CCNP breaks every probed workload the moment any policy selects it.
- **Talos enforces PodSecurity `baseline`; k3s enforced nothing.** Any workload needing `hostPath`, `hostNetwork`, `hostPID` or a `hostPort` needs `pod-security.kubernetes.io/enforce: privileged` on its namespace — currently `storage` (provisioner helper pods) and `observability` (node-exporter). Both failure modes misreport their cause: the storage one fails at the *first PVC* rather than at deploy, and the node-exporter one surfaces as a **HelmRelease timing out on a DaemonSet** with no pod to inspect, because admission rejected the pods before creation. `kubectl describe ds` is where the real message is. Tailscale's proxies pass `baseline` despite `NET_ADMIN` — verified, no exemption needed.
- **Recreating a Tailscale exposure burns a certificate — edit in place instead.** Every `tailscale`-class Ingress (and `loadBalancerClass: tailscale` Service) gets a proxy whose state Secret, `ts-<name>-<random>-0`, caches the issued cert next to its device identity. That Secret is created and destroyed *with the exposure*, so delete-and-recreate always forces a fresh Let's Encrypt order — there is no cross-recreate cache. Five failed attempts on one hostname within an hour trips LE's failed-authorization limit and that hostname serves no TLS until the window clears; each further attempt slides the window forward, so retrying makes it worse. Symptom is a client that hangs rather than errors. Check `kubectl logs -n tailscale ts-<name>-<hash>-0 | grep -i acme` before suspecting your manifest. Note this is *not* the 7-day duplicate-certificate limit that most Tailscale/LE write-ups describe — recovery here is minutes. Full analysis in `docs/external-consumer-access-notes.md`.
- **The apiserver's tailnet proxy is fate-shared with the apiserver, and recovers by crashing.** `kube-apiserver-ci-0` watches its own config Secret through the apiserver and treats a failed watch as **fatal** — so any change that restarts the apiserver (`cluster.apiServer.extraArgs` via `terraform apply`, for one) kills the proxy too. It comes back on restart backoff, taking a few minutes and several `Error` restarts to do it, during which the tailnet path is dead while `kubectl` from the host works fine. Note the `ProxyGroup`'s own status keeps reporting `ProxyGroupReady=True` throughout — it lags reality, so trust `kubectl get pod -n tailscale` and a real request over the tailnet, not the CR's conditions.
- **App-repo isolation lives in a `ValidatingAdmissionPolicy`, not in RBAC — and RBAC will not tell you when it breaks.** CI identities from GitHub OIDC all share one group (`gha:lestherll`, from the `repository_owner` claim) and one `RoleBinding`; that is what makes onboarding a new app free of any change here. What stops repo A touching repo B's objects is `app-registrar-repo-isolation`, which compares the object's name against the repository in the caller's own `sub` claim. Delete or misedit that policy and every CI identity silently gains access to every app's pointer objects, with RBAC still reporting exactly what it did before. It compares with `==` on purpose: `startsWith`/`contains` would let `fastapi-echo-evil` reach `fastapi-echo`. Re-run the test matrix in `docs/zero-touch-app-registration.md` after touching it.
- **The tailnet policy is git-owned, and an admin-console edit to it is drift that the next merge silently overwrites.** `tailscale-acl/policy.hujson` is applied on every push to `main` that touches it. The workflow caches the last-applied ETag so `gitops-pusher` can *notice* a console edit, but it doesn't pass `--fail-on-manual-edits` — the mismatch is reported in the job log and the apply proceeds regardless. To keep a console change, export it into the file first. PRs run the same policy in `test` mode (validate + run its `tests` block) without touching the tailnet, so a rule change gets checked before it can lock anyone out.
- **Two disks, and they are not interchangeable.** `/` is a 128G SSD; `/mnt/storage` is a 931G **5400rpm** spinning disk. Bulk sequential state (object storage) goes on the HDD via the `bulk` class; latency-bound state (Postgres WAL, Prometheus TSDB) goes on the SSD via `fast`. The `bulk_storage` role asserts the disk is mounted before writing — an unmounted `/mnt/storage` would put the VM's bulk disk image on the SSD. That assert is **the only hardware assertion left anywhere in the design**: below it, the cluster knows disk *roles*, never disk *paths*.
- **These PVCs have no quota.** A PV is a plain hostPath directory, so `df` inside a pod reports the whole tier's filesystem and `resources.requests.storage` is documentation, not a limit. The tiers do bound the damage — a runaway on `fast` fills 20 GiB and stops rather than taking the node with it — but within a tier nothing is enforced. Anything that can grow without bound needs an *application-level* cap (e.g. Prometheus `retentionSize`), because the volume will not stop it.
- **The VM's disk images are sparse, and `df` inside the guest can't see the danger.** Declared size is documentation, not a reservation — several thin images can collectively promise more than the host filesystem has, and the guest keeps writing happily until the *host* fills underneath it. `disk-space-watchdog` (part of the `heartbeat_watchdog` role) checks `/` and `/mnt/storage` on the host itself every 30 minutes and posts to ntfy past `disk_space_warn_threshold_percent`; an in-cluster alert would only ever see the guest's wrong view. See LES-102.
- **A Talos node reaches the tailnet by system extension, and an extension changes only at install or upgrade.** `terraform/modules/talos-metal/` renders an `ExtensionServiceConfig` for `siderolabs/tailscale` and adds `<hostname>.<tailnet_domain>` to `machine.certSANs` for every node in its `nodes` map — but `terraform apply` **cannot install the extension**. `apply-config` never re-runs the installer, so a node whose image predates the schematic gets a config naming a service that does not exist and starts nothing, while Terraform reports success and `talosctl get machineconfig` shows the new image. The installed image changes by `talosctl upgrade --image factory.talos.dev/installer/<schematic-id>:<version>` and by nothing else. Two more traps, both verified against containerboot v1.98.9: `TS_AUTH_ONCE` defaults to **false**, meaning every boot re-runs `tailscale up --authkey` against a key Tailscale caps at 90 days; and the ACL destination is `tag:talos`, a **tag**, so a key minted without that tag yields a node that joins as a user-owned device, matches no grant, and reads as "Tailscale is broken". Full runbook: `docs/fleet/talosctl-off-lan.md`.
- **`talosctl upgrade` drains by default, and on this single-node cluster that can never succeed.** `--drain` defaults to **true** with a 5-minute `--drain-timeout`; there is nowhere to evict pods to, and Longhorn's instance-manager PDBs refuse eviction outright. The drain burns its timeout, the **reboot is skipped**, and the node is left **cordoned** — measured 2026-09-03, 41 pods Pending including CoreDNS, Cilium operator, Flux and CNPG. The install succeeds *first*, so both `talosctl`'s `upgrade completed` and dmesg's `upgrade completed successfully: exit_code=0` are true statements about the install and say nothing about the reboot; and nothing uncordons on the way out, so a later `talosctl reboot` does not clear it. Always pass `--drain=false`, then check `kubectl get node` for `SchedulingDisabled`. The only two things that cannot lie about whether an upgrade landed are `talosctl read /proc/uptime` and the schematic ID in `talosctl get extensions`.
- **`terraform apply` for the metal cluster runs from anywhere, and `endpoint` vs `node` is why.** The module defaults to dialling `<hostname>.<tailnet_domain>`, so no control plane is LAN-bound any more. The distinction is the same one `talosctl` draws: `endpoint` is dialled by *your* machine (a MagicDNS name works) and `node` is a routing header resolved by apid *on the node* (a name does not — `.ts.net` is not in `machine.network.nameservers`). Pass `-var dial_over_lan=true` for the two maintenance-mode cases, both hands-on regardless: a first build, and a rebuild after `terraform destroy` — `on_destroy` resets the node, wiping `/var/lib/tailscale` with STATE, so it drops off the tailnet. **Not symmetric with `talosctl`**, which takes a *list* of endpoints and fails over between them (verified: tolerates an unreachable endpoint and an entirely unresolvable one, either order), so `talosctl config endpoint <tailnet-name> <lan-ip>` needs no mode flag; the provider's `endpoint` is a single string.
- **Hardware appears in `fleet/nodes.yaml` and nowhere else — and it is per node because the fleet is not uniform.** Disks, install target and zone used to be module-wide, which silently assumed every machine looked like machine 2; `docs/fleet/hardware-fit-notes.md` §6 records that machine 1 (laptop, 931G HDD, battery) and machine 2 (SFF desktop, one SSD) are near-opposites on every row that matters. Two traps this closes. The install target is a **selector, not a path**: enumeration order is not stable across a disk being added, and machine 2 grows an iSCSI `VIRTUAL-DISK` at runtime (Longhorn's own), so "the first disk" eventually means the wrong one. And Longhorn's `default-disks-config` annotation **only takes effect when the node has no existing disks or tags**, so a shared list that mis-tags a new machine's disks costs a rebuild, not an edit. Adding a machine: a block in that file, then `terraform apply -var 'dial_over_lan=["<name>"]'` while it sits in maintenance mode.
- **A Talos node's Kubernetes identity drifts onto the tailnet unless you stop it, and a `!`-only filter does not stop it.** With `machine.kubelet.nodeIP` unset, Talos deduces `validSubnets` from the service CIDRs — effectively "any address of the right family" — so the kubelet picks by sort order, and `100.x/32` sorts ahead of `192.168.0.x/24`. Measured 2026-09-03: installing the tailscale extension silently moved the node's `InternalIP`, node-exporter's Endpoint and etcd's advertised peer URL (`https://100.105.86.101:2380`) onto the tailnet, with nothing reporting it. The cost is that the node's cluster identity depends on tailscaled — and so on an auth key capped at 90 days — and that a second node would replicate Longhorn and etcd over WireGuard between two machines on the same switch. **The filter form is the trap**: `net.FilterIPs` (used by *both* `machine.kubelet.nodeIP.validSubnets` and `cluster.etcd.advertisedSubnets`) starts from an *empty* set — a positive CIDR adds, a negative subtracts — so a negatives-only list matches **nothing**, and the kubelet then sets no `--node-ip` at all, logging `no suitable node IP found` and nothing else. Positive base first, then subtract: `["0.0.0.0/0", "!100.64.0.0/10"]`. No LAN address appears on purpose — that is what survives a new router (LES-177). Pod/service CIDRs and VIPs need no entry; Talos always excludes them.
- **Reaching a Talos node is not the same as being allowed to.** The tailnet grant is `autogroup:member` → `tag:talos` on `tcp:50000`, so *reachability* covers every device the operator owns, present and future, with no per-device change. `apid` still demands mutual TLS against the Talos PKI — there is no OIDC path, so nothing here resembles the `kubectl` story. Copying the admin `talosconfig` onto each device is the obvious move and the wrong one: use `talosctl config new <file> --roles os:reader --crt-ttl 720h`. Talos has **no CRL**, so revoking a device means waiting out the TTL or rotating the cluster PKI — remote `talosctl` is *more* expensive to keep safe than remote `kubectl`, which is the opposite of where intuition points.
- **MagicDNS names don't resolve from inside pods.** CoreDNS doesn't forward `.ts.net`, though the node itself resolves it fine. A pod that must reach a tailnet name needs explicit `dnsConfig` — worth knowing before debugging a connection failure that is really a DNS failure.
- **node-exporter measures the VM, not the metal.** Everything it reports — CPU, memory, disks, interfaces — describes the guest. `/sys/class/powercap` is empty inside it, so the RAPL series behind `infrastructure/observability/dashboards/power-energy.json` have no source and those panels are dark. Reconnecting them means an exporter on the host (LES-97), not a config change in the chart.
- **Single-user, single-tenant.** No multi-tenancy, quotas, or chargeback — see `CONCEPT.md` if that assumption ever seems wrong. The fleet itself is no longer single-node (D20's bare-metal migration is under way, see the Description above), but the tenancy model hasn't changed.

## Usage
- Bootstrap/converge the host: `ansible-playbook -i ansible/inventory/hosts.ini ansible/playbooks/converge.yml --tags <role>` — no top-level `sudo`, see the escalation note above.
- Cluster access: `kubectl` via `~/.kube/config`. Neither Terraform nor Ansible writes it — Terraform's client configuration is deliberately ephemeral and never touches disk. Regenerate with `talosctl --nodes 10.10.0.10 kubeconfig --force ~/.kube/config`.
- Node access: `talosctl` (no SSH, no shell on the node). A pod that needs to look at a volume directly is `terraform/debug-pod.yaml`.
- **`talosctl` needs a talosconfig, and nothing generates one for you.** An empty `~/.talos/config` fails with `no context is set` / `failed to determine endpoints`, which is a bad thing to discover during an incident — this is the tool for a node with no shell and no SSH. Rebuild it from the SOPS-encrypted PKI:
  ```
  sops --decrypt terraform/clusters/homelab/talos-secrets.sops.yaml > /tmp/secrets.yaml
  talosctl gen config homelab https://10.10.0.10:6443 --with-secrets /tmp/secrets.yaml -o <dir>
  ```
  That writes `talosconfig` alongside two machine configs you can discard; point `TALOSCONFIG` at it (and shred the plaintext secrets). This is why `talos-secrets.sops.yaml` exists as a second copy of the same PKI in talosctl's spelling — see the comment in `.sops.yaml`.

  **Set the ENDPOINT to a tailnet name; leave the NODE an address.** The two are not interchangeable and the failure misreports itself:
  ```
  talosctl config endpoint homelab-worker-0.tailf4742d.ts.net   # dialled by the client — a name works
  talosctl config node     192.168.0.221                        # resolved by apid ON the node — a name does NOT
  ```
  `--nodes` is a routing header apid resolves using `machine.network.nameservers` (`1.1.1.1`/`9.9.9.9`), which know nothing about `.ts.net` — so a MagicDNS name there fails with `name resolver error: produced zero addresses`, which reads like a *client* DNS problem and is not one. `TS_ACCEPT_DNS=false` is what makes that true, and it stays false deliberately. Verified off-LAN 2026-09-03.
  For a *second* device, mint a scoped config — `talosctl config new <file> --roles os:reader --crt-ttl 720h` — rather than copying the admin one.
- Editing an encrypted secret: `sops infrastructure/<path>/<name>.sops.yaml`.
- Reading what a platform-API type renders: `scripts/platform-render eject Application/<name> -n <ns>` (or `preview -f <file>` before applying). Note kro renders in its controller, not in admission, so `kubectl apply --dry-run=server` on an instance shows the instance and nothing downstream — that is the gap this script fills.

## Notes
- Verify idempotency after Ansible role changes by re-running the same `--tags` and checking for `changed=0` in the recap before assuming a fix is "live."
- A new kind added to any `ResourceGraphDefinition` under `platform-api/` needs a matching grant in `platform-api/rbac-kro-aggregate.yaml`, or kro reconciliation fails with a permission error.
- **Removing a kind is the harder direction, and doing it in one change deadlocks kro.** On every reconcile kro lists *orphans* of the kinds it previously rendered, so revoking the grant in the same commit that drops the resource makes that list `forbidden` — which fails the **entire** reconcile, not just the cleanup. Every instance of that RGD parks at `IN_PROGRESS` / `Ready=False` with the permission error in `.status.conditions`, and deleting the leftover objects by hand does **not** clear it, because the forbidden call is the `list` itself. Restoring the grant is the only way out. So: drop the resource from the RGD, let every instance reconcile clean, and remove the grant in a *later* change — the exact mirror of the "RBAC first" ordering in `platform-api/kustomization.yaml`. Observed on a rollback, which is the likeliest way to meet it: reverting an RGD revision reverts its grant too.
